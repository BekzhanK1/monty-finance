# ТЗ: Финализация покупок и готовность блюда (Food)

**Дата:** 2026-05-16  
**Статус:** черновик ТЗ (к реализации после согласования)  
**Основа:** [decisions.md](./decisions.md) (D5, D6, D7), [domains.md](./domains.md), [plan.md](./plan.md) (эпик 3.1.3), обратная связь по UX MVP.

Документ описывает **следующую итерацию** после MVP: удобный цикл «блюдо → что не хватает → список → покупка → кладовая», плюс исправление единиц в составе блюда.

---

## 1. Проблема

| Сейчас | Почему неудобно |
|--------|------------------|
| В списке покупок количество **только для чтения** (расчёт из меню) | В магазине покупают упаковками (1 л), а не «100 мл по рецепту» |
| После покупки остатки **не попадают на склад** | Двойной ввод: список + вкладка «Склад» вручную |
| В каталоге нет сигнала «можно готовить / не хватает» | Непонятно, зачем открывать блюдо и меню |
| В составе блюда единицу можно выбрать **любую** (например «шт» для молока) | Ошибки при генерации списка и сравнении со складом ([D6]) |

**«Завершить» vs «В Finance»** (уже в MVP, не меняем):

| Действие | Результат |
|----------|-----------|
| **Завершить** | Список → `done`, **без** записи в Finance |
| **В Finance** | Сумма `actual_price` по строкам → одна трата в Finance, список `done` + `linked_transaction_id` |

Финализация покупок в этом ТЗ — про **склад и фактические количества**, не про замену Finance.

## 2. Цель итерации

1. На **карточке блюда** в каталоге — индикатор готовности по складу: 🟢 / 🟡 / 🔴.
2. Из блюда — переход/действие **«Недостающее в список»** (не весь каталог).
3. В **списке покупок** — редактировать **количество и единицу** под реальную покупку + цена (как сейчас).
4. После покупки — **пополнение кладовой** из списка (по факту купленного количества).
5. При добавлении продукта в **состав блюда** — **по умолчанию единица продукта** (`Ingredient.default_unit_id`), без случайного «шт» для молока.

## 3. Новые продуктовые решения

### D11. Единица в составе блюда = default продукта

**Решение:** при выборе ингредиента в редакторе блюда поле **«Единица»** автоматически = `ingredient.default_unit_id` (молоко → мл, если так заведено в справочнике).

- Смена продукта в строке → единица **перезаписывается** на default нового продукта.
- Ручная смена единицы **допускается** (редкие рецепты), с подсказкой: «Обычно для этого продукта: мл».
- Backend при `PUT /dishes/{id}/ingredients` **не меняет** правило: любая валидная `unit_id` принимается; валидация «рекомендуемой» единицы — только UI.

### D12. Статус готовности блюда по складу

**Решение:** три состояния на уровне **блюда** (для `servings_default` порций, без привязки к слоту меню):

| Статус | UI | Условие (все строки состава с `ingredient_id`, кроме `is_pantry_default` без `is_optional`) |
|--------|-----|-------------------------------------------------------------------------------------------|
| `ready` | 🟢 зелёная галочка | На складе в **той же** `(ingredient_id, unit_id)` достаточно: `pantry.qty >= line.qty` |
| `partial` | 🟡 жёлтый | Есть хотя бы одна строка с достаточным остатком **или** остаток в **другой** единице (как [D6]) |
| `missing` | 🔴 красный | Нет состава **или** ни по одной нужной строке нет достаточного остатка в той же единице |

Строки с `is_pantry_default` и без `is_optional` **не участвуют** в расчёте (как в генераторе [D5]).

Пустой состав → `missing` (или отдельный серый «без состава» — на усмотрение UI).

### D13. Пополнение кладовой после покупки

**Решение:**

- При отметке строки **«куплено»** (`checked=true`) и наличии `ingredient_id` — показать действие **«+ на склад»** (или чекбокс «добавить на склад», default **вкл**).
- На склад идёт **фактическое** `quantity` + `unit_id` из строки списка (после правки пользователем), не расчётное из меню.
- Логика склада — как `POST /food/pantry` upsert: та же единица → **сложить**; другая единица → ошибка с текстом как сейчас.
- Повторное «+ на склад» для той же строки **не дублирует** (флаг `pantry_applied` на item или отдельная таблица — см. §6).
- Массовое действие: **«Отправить купленное на склад»** по всем отмеченным и ещё не отправленным строкам с `ingredient_id`.

## 4. Пользовательские сценарии

### 4.1 Каталог — видно, что можно готовить

1. Пользователь открывает **Каталог**.
2. У каждого блюда с составом — badge 🟢/🟡/🔴 + короткий текст («всё есть» / «частично» / «купить»).
3. Тап по блюду → карточка/модалка: состав, что есть на складе, что не хватает.
4. Кнопка **«Недостающее в список»**:
   - если нет активного/черновика списка на текущую неделю — создать или предложить «Собрать на неделю»;
   - добавить в список только позиции с `need > 0` для **этого блюда** (порции = `servings_default`), с учётом склада ([D6]).
5. Переход на вкладку **Список** с подсветкой добавленных строк (опционально).

### 4.2 Список — покупка как в магазине

1. Строка из меню: «Молоко 100 мл» → пользователь меняет на **1000 мл** (или 1 л, если есть единица).
2. Вписывает **цену** → при необходимости **«В Finance»**.
3. Ставит **куплено** → срабатывает **«+ на склад»** (+1000 мл молока).
4. Возврат в каталог — блюдо с молоком ближе к 🟢 (если остального хватает).

### 4.3 Склад ↔ меню (без изменений правил D6)

- Генерация списка на неделю по-прежнему: `нужно − склад` в **одинаковой** единице.
- Редактирование количества в списке **не меняет** рецепт блюда — только факт покупки и остаток.

## 6. Backend

### 6.1 API (новое / расширение)

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/food/dishes?include_pantry_status=true` | В ответе `pantry_status: ready\|partial\|missing` на каждое блюдо |
| GET | `/food/dishes/{id}/pantry-breakdown` | Детализация по строкам состава (опционально, если список тяжёлый) |
| POST | `/food/dishes/{id}/shopping-shortfall` | Добавить недостающее по **одному** блюду в текущий draft/active список |
| PATCH | `/food/shopping-items/{id}` | + `quantity`, `unit_id` (расширение) |
| POST | `/food/shopping-lists/{id}/apply-to-pantry` | Body: `{ item_ids?: number[] }` — upsert на склад для checked + не applied |

### 6.2 Модель данных

**Вариант A (минимальный):** колонка на позиции списка:

```text
food_shopping_items.pantry_applied_at  TIMESTAMP NULL
```

**Вариант B:** отдельная связь `food_shopping_pantry_log` — если нужен аудит; для MVP достаточно A.

### 6.3 Сервис `dish_pantry_status.py`

Вход: `household_id`, блюдо с `ingredients[]`, карта склада `load_pantry_by_ingredient_unit` (как в `pantry_adjust.py`).

Для каждой строки состава (с фильтром [D5]):

- `sufficient` — та же единица, `stock >= qty`
- `unit_mismatch` — есть stock по `ingredient_id`, другая `unit_id`
- `absent` — нет в той же единице и нет «чужой» единицы → need полностью
- `absent` + other unit → `unit_mismatch`

Агрегация:

- все учтённые строки `sufficient` → `ready`
- ни одной `sufficient`, есть `unit_mismatch` или частичный mix → `partial`
- иначе → `missing`

### 6.4 `shopping-shortfall` для одного блюда

- Посчитать потребность по составу × `servings_default`.
- Вычесть склад ([D6]).
- Для каждого `(ingredient_id, unit_id)` с `net > 0` — добавить/увеличить строку в **текущем** списке (`draft` или `active` на период недели); если списка нет — 400 с hint «сначала соберите список на неделю».

### 6.5 `apply-to-pantry`

- Только items с `ingredient_id`, `checked=true`, `pantry_applied_at IS NULL`.
- Upsert через существующую логику pantry router.
- Проставить `pantry_applied_at`.

## 9. Критерии приёмки

- [x] Молоко в справочнике с default **мл** → в новой строке состава блюда единица **мл**, не «шт».
- [x] Блюдо с полным складом под `servings_default` → 🟢 в каталоге.
- [x] Блюдо без состава → 🔴 (или отдельное «нет состава»).
- [x] В списке можно изменить 100 мл → 1000 мл, цена сохраняется.
- [x] После «куплено» + «на склад» остаток на вкладке **Склад** увеличился на **1000 мл**.
- [x] Повторное применение той же строки на склад **не удваивает** остаток.
- [x] «В Finance» и «Завершить» работают как до итерации.
- [x] «Недостающее в список» добавляет только deficit по этому блюду, не дублирует лишнее при повторном нажатии (merge по ingredient+unit или increment qty).

## 10. Вне скоупа

- Конвертация единиц (мл ↔ л автоматически) — по-прежнему [D6] фаза 2+.
- Режим «в магазине» (4.3), теги, шаблоны, AI.
- Автоматическое списание со склада после готовки.
- Изменение `servings` слота в расчёте статуса блюда в каталоге (только `servings_default`; в меню — отдельная фаза).
